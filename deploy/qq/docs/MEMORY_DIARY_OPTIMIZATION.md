# 长期记忆与独立日记优化

审计与实施：2026-10-26，MaiBot 1.3.15，社交生活插件升级至 0.9.0。对应需求：[REQUIREMENTS-3.md](REQUIREMENTS-3.md)。本次没有更改人格、普通聊天频率、QQ 登录方式或空间行为，也没有删除记忆、重建向量或迁移数据库。现有插件运行时会因源码修改自动热加载；Docker 容器未因此重启。

## 1. 实际记忆数据流

```text
真实 QQ / 本地消息 → MaiBot.db / mai_messages
  ├─ 最近群聊30条 / 私聊40条 → Planner → 本地Replyer
  ├─ 已回复用户的直接自述 → Utils提取 → 证据校验 / 持久幂等
  │    → person_fact 段落 / Fact Claim → 人物画像版本
  └─ 会话新增60条 → Memory增量摘要 → 段落 + 实体 / 关系
       ├─ CPU Embedding → paragraph / graph 双向量池 + FTS检索
       ├─ Episode：关联原摘要证据的情景层
       └─ 有明确人物绑定的证据 → 人物画像

人物画像 / 启发式回想 / query_memory → Planner内部上下文
query_memory结果的replyer_memory_reference → Replyer背景
上下文过长 → Planner压缩状态 → 当前推理上下文；不是再写一份长期事实

允许的当天消息 → 私人事件整理 → 私人日记文件
                 ↑可读取既有记忆     ╳不反向写回记忆或聊天
```

| 层 | 输入、触发与职责 | 实际存储及限制 |
|---|---|---|
| 近期消息 | 真实会话消息，供当轮理解；不等于长期记忆 | `data/MaiMBot/MaiBot.db` 的 `mai_messages`、`chat_sessions` |
| Chat Summary | 每流新增60条后生成增量，参考前两条摘要判断新增／更正，不是两次独立审核 | `a-memorix/metadata/metadata.db` 的 `paragraphs`，来源 `chat_summary:<真实会话ID>`；空增量正常 |
| Person Fact | 机器人回复后，对目标用户原始自述用 Utils 提取；须有真实证据ID、完整原句及明确归属；一次最多5项 | 同库 `person_fact` 段落、`fact_claims` 等；`person_fact_writeback.sqlite3` 保存处理幂等，不是第二套记忆内容库 |
| Person Profile | 人物证据、关系和事实账本的可更新视图；30分钟维护周期、活跃窗口72小时、证据Top-8 | `person_profile_snapshots` 是版本，不是每版都新增事实；自动注入最多1人；旧摘要缺少人物绑定时不会凭昵称强行归人 |
| Episode | 在24小时来源窗口中聚合段落并保存事件、参与者、关键词与证据引用 | `episodes`、`episode_paragraphs`；已排除 `person_fact` 来源，不重复把稳定事实当事件生成 |
| Graph | 已确认实体与关系，用于关系线索扩展、图检索及衰减 | `entities`、`relations`、`paragraph_entities`、`paragraph_relations`；关系三元组有唯一约束 |
| Embedding | bge-small-zh-v1.5，CPU、512维，结合语义、FTS及图候选排序 | `a-memorix/vectors/spaces/`，双池；不能仅凭旧 `paragraphs.vector_index` 为空判断无向量，实际使用独立空间索引 |
| Mid Memory | 当前版本没有该任务槽位；`context/compaction.py` 调用 `planner` 生成状态压缩 | 供当前上下文延续；没有为此添加虚构配置或第二条长期写回链 |

路径前缀：上述 `a-memorix/` 均在 `data/MaiMBot/` 下。源代码定位：`src/services/memory_flow_service.py`、`person_fact_policy.py`、`person_fact_journal.py`、`src/A_memorix/host_service.py`、`core/utils/person_profile_service.py`、`src/maisaka/memory/`、`builtin_tool/query_memory.py`、`context/compaction.py`。

## 2. 已确认问题与证据

### 摘要覆盖窗口确有缺口

旧配置每新增60条触发，却只读取40条。库内9条摘要元数据记录的 pending 为60–65、context均为40；其中包含已删除摘要。每轮有20–25条不在该次窗口内，但不能由此断言这些消息全部包含重要事实。

已将真实运行配置及部署模板的 `chat_summary_writeback_context_length` 改成120，触发阈值仍为60。现有实现实际读取 `min(120, pending)`，通常覆盖本轮新增消息，不因120而重复读取旧窗口。它增加单次材料，不增加调用频率。若长期积压超过120条仍可能截断；本次不冒险重写核心游标算法，也没有自动补写历史遗漏。

### 不能把全部“重复”都当作重复入库

审计时共16条段落：8条有效摘要、8条已删除记录；后者包含此前撤回的7条人物事实。7个 Fact Claim 均为 retracted，未被复活。有效段落完全相同正文的冗余为0，关系三元组完全重复为0。另有8条Episode、13个人物的24版画像。

3条原文检索探针中，有1组结果存在一对文本相似度≥0.8的 Episode／段落。它说明展示候选可能重复，不能仅凭文本相似度删除某层证据：摘要和事件是不同表示，也可能包含更新后的状态。本次没有放大Top-K、批量合并实体、清空历史或关闭记忆层。

### 原日记路径无法覆盖全天

旧路径每6小时最多25条消息，再保留最多4个场景并选1–2个。它虽然分时段读取，仍会丢失许多允许素材；旧版统一拒绝引号也会误伤自然的短引用。已在插件内替换为可独立启用的全天分批事件路径，旧路径保留作回退。

## 3. 重要性、身份、去重、更新与遗忘

沿用现有准入规则：稳定偏好、方向、关系等直接自述进入人物事实候选；共同经历、约定与变化由摘要／事件承载；临时玩笑、测试、猜测、转述和机器人自行推断不晋升为用户稳定属性。重要性不等于重复次数，不额外为每条普通消息再调用一次完整分析。

人物事实按真实平台／人物／会话／证据消息持久幂等，解决回复分段重复提取；原文规范化去重解决相同表达，不能保证任意近义句语义合并。Fact Claim 有状态、时间与变更记录，但自动提取并不保证每种偏好变化都能对齐同一个语义键。自动反馈纠错及模糊修改自动执行仍关闭；旧事实纠正宜使用原生管理页确认后操作。本次不根据不完整证据覆盖任何历史事实。

私聊直接自述的“你／您”绑定机器人实际名字；群聊受话者不明确时拒绝写稳定事实。机器人回复只供上下文，不作为用户事实证据。保守的完整原句／临时性过滤也可能漏掉表达复杂的重要信息；不能承诺重要信息全部自动入库。

“遗忘”主要是关系维护：24小时半衰期，强度低于0.1冻结，冻结24小时后符合条件的关系可归档；访问和明确强化会提高保留强度，保护／固定的关系例外。它不是把全部聊天、摘要或画像每24小时删除。未设到期时间的段落仍可能保留并被检索，因此关系衰减并不保证自动清掉所有琐事。没有调整这些维护参数。

## 4. 检索与使用：分开判断

- **写入问题**：源证据是否曾被窗口覆盖、是否被准入规则拒绝、阈值是否尚未达到、幂等状态或写入错误是什么。
- **检索问题**：段落确实存在，再检查身份／时间／来源过滤、向量健康和排序；不是先扩大Top-K。
- **使用问题**：检索结果已进入Planner／Replyer，再检查模型是否忽略、误读人物或把过去当现在。

当前自动回想按最近20条形成线索，最多注入3条、900字，间隔至少180秒；已有状态还受60条新消息门槛，缓存300秒。原生 `query_memory` 默认5条，并有结构化结果向Replyer透传；画像注入与启发式回想不是同一入口。全局共享开启后工具检索可以跨会话，但启发式回想还有额外的来源过滤，不能把两者混为同一个共享开关。

**隐私边界保留风险**：本次已明确询问，你选择“暂时保留当前共享，仅记录风险”。全局长期记忆仍双向共享，画像也不能保证逐条区分公开与私聊秘密；Prompt约束不是访问控制。没有将其描述为已解决的细粒度权限。私人日记文件与素材不纳入共享。

## 5. 两阶段私人日记

详见 [日记机制](DIARY_MECHANISM.md)。当天允许消息按小时无条数采样上限读取，媒体、通知、敏感内容和明确验收消息仍过滤；单条正文最长1200字并标记截断。可用消息超过5000或分批超过24次时明确失败，不悄悄丢弃一天末尾。

DeepSeek Flash：分批整理场景引用、主题、意义、重要程度与氛围，不写日记、不自行改写说话人；同话题连续片段可以合并。输入共享人物映射和消息列名，降低结构开销。完整场景、原始整理结果和指标独立保存，写作只采用最多两个主题与有界历史背景。

Qwen3-8B：当前无固定字数，由角色根据当天素材和表达内容自行决定篇幅，事实背景最多一句，围绕一个细节写自己的观察、疑问或联想，不逐项汇报全天事件。可引用少量有证据的短句；虚拟日程是设定。没有改动真实人格或添加固定日记模板。

虚拟日程来自现有 `life_state`。社交插件的情绪／关系数值及登记事件维持原用途，日记没有把这些分数或登记条目另行当作真实聊天事实；没有第二个日记生成器。

每天仍21:00开始，故只覆盖截至生成时的当天材料；若要严格覆盖自然日，需要另行改到次日生成。重启不重复领取；失败保留阶段与错误，管理员显式重试；手动重新创作使用新的预览revision，不覆盖旧日记。新流程在投递函数中禁止QQ日记发送，既不回流聊天记忆，也不公开到空间。

管理员认证页面可按日期查询，CLI支持预览、查看、编辑和归档。编辑须提供当前文件SHA-256，先保存旧版再原子替换；归档保留可恢复副本，不永久删除。没有实际执行任何已有日记的修改或归档。

## 6. 验证与准确性边界

匿名统计在 [`../memory-diary/verification.json`](../memory-diary/verification.json)，不含聊天原文、私人日记正文或账号凭据。

- 记忆修复及摘要集成目标回归：21项通过，使用临时实例数据库。
- 插件回归覆盖全天完整读取、人物／回复ID、事件ID验证、压缩输入等价、不可覆盖、编辑归档版本保护、错误记录与不发送QQ。
- Embedding自检：配置、检测、索引维度均512，runtime/retrieval ready，非降级状态。
- 三条已保存摘要原文探针：目标均在Top-3，最近一轮耗时约0.02–0.06秒；这是索引／原文查询检查，不是自然提问召回率。
- 12条明确标注的合成样本，稳定属性4条均获正确准入，7条临时／他人／假设材料均未准入；1条共同部署经历未被当作稳定属性，在独立摘要草稿测试中被保留。两种提取职责不同。这里的4/4与0次误准入样本很小，并且没有写入生产库，不能称为生产写入准确率。
- 本地Qwen对两条合成参考事实的离线回答包含期望的学科与游戏关键词。这只验证基本背景使用，不能证明实际聊天中的语义正确率。
- 历史消息未逐条人工标注“应记／不应记”，因此真实重要信息召回率、写入准确率、自然提问召回率暂无可靠百分比。
- 对照测试的正式日记哈希不变，所有测试预览与事件产物独立保存，没有真实QQ测试发送，也没有把合成事实／测试日记导入记忆。

两天历史完整流程及最新最终测试的具体指标见下方验证补记。第一次全文预览中自动审阅曾标出1个疑似无依据事件；收紧主题与事实背景后，两篇写作对照均未再被标出人物错配或无依据事件。自动审阅不是人工真值或完整事实证明。

对照文件均在 `data/MaiMBot-plugin-data/jycao.social-life/`：正式旧日记 `diaries/`（并非两天均必有原稿）；完整流程初稿 `diary-previews-req3-v4/`；复用已整理全天事件的写作对照 `diary-previews-req3-v5/`（仅重写、未再次检索历史记忆）；新压缩输入流程 `diary-previews-req3-v6/`。失败任务也保留，不伪装为成功。文件属于私人资料，请本地查看，不要提交Git或公开。

## 7. 模型与性能

实际模型路由保留：Replyer=本地Qwen3-8B，Planner/Memory/Utils=DeepSeek Flash，Embedding=bge-small-zh-cpu；Memory/Utils温度0.3。事件整理显式温度0.2，写作0.8。不创建 `mid_memory` 字段，不额外加载GPU模型或安装大型依赖。

初版完整测试：10月24日293条可用消息、42场景，6次事件请求加1次Qwen，约19.5秒；10月25日796条、131场景，17次事件请求加1次Qwen，约59.4秒。重复的结构元数据开销较大，随后改成共享人物表／列名；同一素材最终所需事件请求减少到3次和8次。全部素材仍进入批次，减少的是重复元数据，不是通过删掉前半天实现。

初版两天事件整理合计输入87311、输出5324Token；最终压缩版数值见补记。生产每天请求数随真实消息量而变，最多24个事件请求，Qwen写作1次，另有最多2次记忆只读检索（CPU Embedding等）。不是每条消息一次云请求；安静无可用消息时不调用事件整理。

插件内部后台模型任务串行，但聊天主生成不共享该锁；Qwen服务仍只有一个并发槽，因此写日记约5–7秒时可能使聊天请求排队。本次没有在真实QQ群进行延迟压测，不能声称群聊延迟完全不受影响。

测试中曾出现一次写作RPC超时，同时核心主循环约81.56秒、WebUI约39.67秒卡顿；没有足够证据判定具体阻塞栈或归因于WSL。保留失败任务，未重启容器或放宽超时掩盖错误。后续单独复验结果见补记。此项作为未解决的运行风险记录。

统计入口：`manage.py status`；`diary-events` 是实际事件模型请求计数，`diary-writing` 是新流程写作请求计数，`diary`/`diary-preview` 是整项任务计数，不能把所有行简单相加当模型次数。事件JSON含逐阶段时长、Token、错误和私人输入／草稿。原生 `model_task_usage` 与 `statistics_model_hourly` 仍统计SDK调用；离线直连模型的测试单独记在 verification.json，不混称已经计入原生统计。
