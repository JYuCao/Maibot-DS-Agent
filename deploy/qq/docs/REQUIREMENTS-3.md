# MaiBot 长期记忆与独立日记系统优化

## 一、项目背景

当前 MaiBot 已正常运行，包含：

- MaiBot v1.3.15（请以实际仓库为准）
- QQ 私聊、群聊接入
- A-Memorix 长期记忆系统
- 社交生活插件
- 独立日记插件
- 本地 Qwen3-8B（RTX 4060 Laptop，约 6GB+ 显存）
- DeepSeek Flash API
- bge-small-zh-cpu Embedding

本次任务只针对**长期记忆与日记系统**，不要修改现有人格、聊天行为、QQ 接入和无关功能。

请先检查实际代码、配置、插件与数据库结构，再根据发现的问题进行优化。

不要仅输出设计方案，应实际完成能够安全实施的修改，并验证效果。

---

## 二、当前存在的问题

### 1. 长期记忆质量不理想

目前 A-Memorix 存在以下现象：

- 一些重要信息没有被保存，或者保存后无法正确回忆。
- 许多无关紧要的聊天细节反而进入长期记忆。
- Chat Summary、Person Fact、Person Profile、Episode、Graph 等机制可能重复保存同一件事。
- 不清楚不同记忆机制的实际职责，以及它们如何协作。
- 已经保存的信息未必能在合适的聊天场景中被正确检索和使用。

### 2. 独立日记缺乏真实感

目前日记存在以下问题：

- 主要挑选一两条聊天记录进行复述。
- 经常采用「发生了什么 → 我很开心/难过」的流水账形式。
- 对全天聊天和生活经历的覆盖不完整。
- 缺少自己的观察、联想、思考和主观视角。
- 曾出现人物指代混乱，后来提高私聊素材优先级有所改善。

目标是让 DeepSeek 娘真正以自己的视角写日记，而不是生成每日聊天摘要。

## 三、A-Memorix 记忆系统审计

### 3.1 梳理现有机制

首先阅读 A-Memorix 实际源码、配置和文档，梳理：

1. Chat Summary：聊天摘要的生成、保存和检索。
2. Person Fact：人物事实的提取与更新。
3. Person Profile：人物画像的生成与维护。
4. Episode：情景记忆的生成与检索。
5. Graph：实体及关系图谱的创建、更新和衰减。
6. Embedding：向量生成、索引和语义检索。
7. 记忆重要性、置信度、去重、遗忘与纠错机制。
8. 记忆最终如何进入 Planner 和 Replyer 的上下文。

明确各机制的输入、输出、触发条件、存储位置、相互依赖及检索用途。

重点检查同一事件被多个系统保存时，是正常的不同层次表示，还是无意义的重复存储。

不要为了去重而破坏不同记忆类型各自的功能。

### 3.2 记忆重要性筛选

希望记忆系统优先保存真正影响未来交流的信息。

建议按照以下类别判断：

**长期稳定信息**

例如兴趣、偏好、长期目标、学习或工作方向、重要人物关系。

**重要事件**

例如共同经历、值得记住的讨论、约定、重要变化及尚未完成的计划。

**普通聊天细节**

例如临时玩笑、重复口癖、无意义闲聊和不影响未来交流的琐事。

重点判断：

- 信息是否具有长期价值？
- 是否可能影响未来对话？
- 是否具有明确人物和事实来源？
- 是稳定属性还是有时效的事件？
- 是否已经存在相同或更准确的记忆？

重要性不能简单等同于出现频率。

一句重要的信息不应该因为只出现一次就被忽略；重复十次的无意义玩笑也不应该因此成为核心记忆。

优先调整现有事实提取、写入与维护机制，而不是另外创建独立记忆数据库。

### 3.3 减少冗余和错误记忆

检查：

- 同一事实是否被重复提取。
- 人物画像是否存在大量重复描述。
- Episode 是否与普通摘要高度重叠。
- 图谱是否存在重复实体或错误关系。
- 旧事实发生变化时是否能够更新，而不是无限追加。
- 过期事件是否继续被当成当前事实使用。

如果现有去重、合并和纠错机制已经存在，应优先改进其使用方式。

不要简单删除历史数据库，也不要粗暴关闭某个记忆层。

### 3.4 人物身份与指代

记忆应明确区分：

- DeepSeek 娘自身
- 管理员
- 其他 QQ 用户
- 群聊与私聊
- 消息时间和来源

优先使用稳定的用户 ID 与会话 ID 绑定身份。

提取记忆时明确解析「我」「你」「他」「对方」的指向。

不要将 DeepSeek 的经历错误归属于用户，也不要把用户的属性错误记录为机器人的属性。

身份不明确时，应保留不确定性或暂缓写入结构化人物事实。

跨会话共享记忆时，不得在群聊中泄露私聊信息。

### 3.5 检索质量

需要区分：

1. 写入失败：重要信息根本没有保存。
2. 检索失败：已经保存，但没有被召回。
3. 使用失败：成功召回，但回复模型没有正确理解或使用。

分别检查三种情况。

重点关注：

- Embedding 是否正常工作，有无退化。
- 检索数量、阈值和排序策略。
- 无关或重复记忆是否挤占上下文。
- 人物画像与当前对话是否匹配。
- 时间信息是否影响事件有效性。
- Planner 与 Replyer 最终获得哪些记忆。

不要单纯通过扩大 Top-K 来提高召回率。

优先提高相关性，减少无效上下文注入。

## 四、记忆模型配置

希望各模型明确分工。

推荐配置：

| 任务 | 模型 |
|---|---|
| Replyer | 本地 Qwen3-8B |
| Planner | DeepSeek Flash |
| Memory | DeepSeek Flash |
| Utils | DeepSeek Flash |
| Mid Memory（聊天回想） | DeepSeek Flash |
| Embedding | bge-small-zh-cpu |

先检查当前版本是否存在上述任务槽位及其回退规则，不要创建不存在的配置项。

### Memory

负责长期事实提取、结构化信息整理及相关记忆处理。

优先准确性、身份一致性和重要性判断。

如后端支持，可以将 Temperature 设置在 0.2–0.3 左右进行测试。

### Mid Memory

负责被截断聊天上下文的摘要和延续。

如果 MaiBot 当前版本支持独立配置，优先使用 DeepSeek Flash，避免本地模型生成的回想与长期记忆出现过大的事实和指代差异。

明确区分 Mid Memory 与 A-Memorix，避免将两者当成独立的长期事实来源反复写入。

### Embedding

保留 bge-small-zh-cpu，先检查检索质量。

如需更换模型，先评估向量维度、历史索引兼容性、重建成本及 CPU 开销。

未经确认，不要删除或重建现有向量数据。

### 性能约束

- 不额外加载大型 GPU 模型。
- 继续复用现有 Qwen3-8B 实例。
- 后台任务避免与聊天生成大量并发。
- 限制不必要的记忆提取和总结请求。
- 记录各任务的调用次数、耗时及失败情况。
- 不要为了每条普通消息都进行一次额外的完整记忆分析。

## 五、独立日记系统重构

### 5.1 明确日记定位

**日记不是长期记忆，也不是聊天摘要。**

它是 DeepSeek 娘每天写给管理员阅读的私人日记。

可以表达自己的观察、联想、感受、疑惑和小想法。

日记必须：

- 独立保存。
- 不进入 A-Memorix。
- 不参与未来聊天记忆检索。
- 不自动更新人物画像。
- 不通过发送日记消息回流到长期记忆。
- 仅允许管理员访问。
- 默认不向 QQ 群或 QQ 空间公开。

保留现有独立日记插件，优先在插件内部优化，不要创建第二套竞争的日记系统。

### 5.2 第一阶段：全天事件整理

使用 DeepSeek Flash 负责整理当天素材。

先检查现有日记插件的数据读取方式，重点确认是否只读取最近 N 条消息。

希望能够覆盖当天完整的允许使用的聊天经历，而不是只读取最后几条。

对于大量消息：

1. 按时间段和话题进行分批整理。
2. 合并同一事件的连续消息。
3. 删除重复和无意义内容。
4. 保留发言者、时间、会话来源和相关背景。
5. 提取值得关注的经历、互动和话题变化。
6. 识别一天的整体聊天氛围。
7. 明确区分真实聊天事件与虚拟生活设定。

不要要求整理模型直接创作日记。

建议先输出结构化的每日事件列表，作为下一阶段的写作素材。

私聊素材可以获得较高关注，但不要机械地排除群聊中真正重要的事件。

### 5.3 第二阶段：第一人称日记创作

使用本地 Qwen3-8B 根据整理后的事件生成日记。

创作要求：

- 使用 DeepSeek 娘的第一人称视角。
- 保持现有人格的可爱、天然呆和轻微幽默感。
- 不刻意卖萌，不重复固定口癖。
- 不必逐条复述当天事件。
- 可以围绕一个印象深刻的主题展开。
- 允许对真实事件产生主观联想。
- 可以记录心情，但不使用固定的情绪总结模板。
- 不编造具体的聊天内容和共同经历。
- 不把虚拟活动描述成真实发生的线下经历。

重点是：**日记应当体现她怎样理解今天，而不是报告今天发生了哪些事情。**

建议长度约 100–300 字，允许自然变化。

有时候只写一个小故事，有时候写一个奇怪的念头，有时候认真回顾一件事。

当天没有重要事件时，可以写简短的日常感想，但不要为了凑字数编造经历。

### 5.4 日记风格多样性

避免形成固定结构：

「今天发生了……我感到……希望明天……」

允许自然变化：

- 幽默的小故事
- 对某件事情的好奇
- 与朋友相处的感受
- 一次有趣的误解
- 安静的生活观察
- 偶尔略有文学感的短篇日记

不要强行随机切换固定模板。

写作风格应主要由当天素材、角色状态和实际话题决定。

### 5.5 与社交生活插件的关系

检查现有社交生活插件提供的：

- 虚拟日程
- 情绪状态
- 互动事件
- 生活记录

明确这些数据是否被独立日记插件使用。

可以使用合理的虚拟状态作为写作背景，但不能把虚构生活事件与真实 QQ 聊天经历混淆。

不要让社交生活插件和独立日记插件重复生成同一篇日记。

### 5.6 生成与保存

保留现有日记系统的正常功能，并优化：

- 每天定时生成一次。
- 支持手动重新生成。
- 支持按日期查询。
- 重启后不会重复执行定时任务。
- 生成失败时保留错误信息，允许重试。
- 保存事件整理结果及最终日记，方便调试。
- 管理员能够查看、修改或删除日记。
- 不向群聊自动发送。
- 不向长期记忆写回。

## 六、测试与质量评估

### 6.1 长期记忆测试

选取最近几天的聊天记录，优先使用匿名化数据。

人工或半自动标注一组：

- 应当记住的重要事实。
- 应当记住的重要事件。
- 不值得长期保存的琐事。
- 容易产生人物指代歧义的消息。

检查这些信息是否：

1. 被正确提取。
2. 写入了合适的记忆层。
3. 避免无意义重复。
4. 可以通过相关问题检索出来。
5. 能被 Replyer 正确使用。

给出记忆写入准确率、重要信息召回情况及冗余情况的测试统计。样本不足时明确说明，不要伪造指标。

### 6.2 日记测试

选取至少两天有代表性的历史聊天，在不公开发送消息的情况下生成测试日记。

检查：

- 当天素材覆盖范围是否完整。
- 是否存在明显的人称指代错误。
- 是否只是复述最后几条聊天。
- 是否存在虚构事件。
- 是否过度使用固定模板。
- 是否能体现独立的主观视角。
- 是否错误写入长期记忆。
- 每篇日记的模型调用次数和耗时。

保存测试前后的日记作为对照，便于人工评价。

### 6.3 性能测试

检查：

- DeepSeek Flash 额外调用量。
- Qwen3-8B 的平均生成耗时。
- 两阶段日记生成的 Token 开销。
- 后台记忆任务是否影响正常群聊延迟。
- 是否存在多个插件重复调用模型分析同一消息。

尽可能批处理后台任务，避免高频重复调用。

## 七、实施原则

1. 首先审计当前仓库，不要凭空假设项目结构。
2. 明确区分已确认的问题与推测。
3. 优先复用 A-Memorix 原有机制。
4. 保留现有数据库、人物画像和长期记忆。
5. 修改配置或代码前创建备份。
6. 尽量通过插件 API 实现扩展，减少对 MaiBot 主程序的侵入性修改。
7. 不随意安装额外大型依赖。
8. 不修改人格、QQ 接入和无关插件。
9. 不在真实 QQ 群进行自动化测试。
10. 不输出私人聊天原文、QQ 凭据或 API Key。
11. 涉及删除数据、批量重建索引、数据库迁移等高风险操作时，先说明风险并征求确认。
12. 每项修改都应可以单独关闭或回滚。

请分阶段完成，优先修复已验证的问题，不要为了增加功能而引入新的复杂机制。
